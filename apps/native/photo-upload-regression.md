# Регрессия загрузки фотографий в воспоминания — 2026-11-16

Проверена цепочка выбора файлов → подготовка в WebView → Android foreground
service → multipart → EXIF → создание воспоминания → перечитывание → очередь обработки.
Также просмотрена общая серверная цепочка и загрузка через браузер/десктоп.

## Найдено и исправлено

- Ответ multipart возвращался до EXIF. Android создавал воспоминание с `timestamp=null`.
  Теперь для фото воспоминаний метаданные извлекаются и сохраняются до ответа.
  Превью продолжают готовиться асинхронно; их задержка/ошибка не стирает уже
  сохранённую дату съёмки. Исходник и разобранный EXIF повторно используются
  при фоновой обработке, без повторного чтения S3 и разбора EXIF.
- Серверная проекция воспоминаний теряла часовой пояс. Теперь сохраняются offset
  и технический размер оригинала. Последний нужен для проверки повторного выбора:
  `sizeBytes` может включать превью и не совпадать с размером исходника.
- JS мог начать следующую пачку, когда предыдущий Android service ещё завершался.
  В статус добавлена готовность сервиса к новому запуску; наблюдатель ждёт её.
- Отмена до `onCreate` сервиса терялась. Флаг отмены теперь записывается в job
  и проверяется перед запуском worker.
- Отмена во время подготовки/удаление ошибки оставляли временные файлы/URL.
  Подготовленные отменённые файлы удаляются; object URL освобождается.
  Пустой файл получает отдельную ошибку, не срывая старт всей пачки.
- Смена аккаунта во время подготовки могла привести к запуску со свежими токенами
  для старой пачки. Перед запуском и при наблюдении проверяется контекст;
  автоматический запуск следующей пачки после смены аккаунта запрещён.
- Поздний ответ fetch/desktop upload мог попасть в другой открытый trip.
  Обновление списка ограничено исходным путешествием.
- Изменяемые JSONObject из worker попадали в статус без независимого снимка.
  Статус теперь копирует элементы под lock; запись результата image и чтение
  отмены синхронизированы с ним.
- Очередь ошибочно называла все фото с EXIF, но без назначенного timestamp,
  «снятыми в другой день». Подпись и фильтр теперь описывают фактическое состояние.

## Проверено автоматически

- Настоящий JPEG с EXIF: 16 ноября 15:12, offset +08:00 → takenAt 07:12 UTC.
  Проверено также при серверном TZ=Asia/Taipei; фото без EXIF остаётся без даты.
- Серверный тест задержанного EXIF: завершение ждёт EXIF, но не ждёт превью.
- PostgreSQL на одноразовой мигрированной БД: create/list/update/assign/unassign,
  offsets +480/0/-300/отсутствует, технический размер, повтор создания той же image
  с сохранением существующего комментария (144 проверки).
- JS bridge: штатное завершение, ожидание освобождения service, пустой файл,
  смена аккаунта при staging, отмена при staging.
- Настоящий Kotlin MemoryUploader с локальным HTTP-сервером: части дают точные
  исходные байты; ошибка memory.create → повтор только создания; UTC+08, UTC-05,
  UTC, переход полуночи, дата вне путешествия, отсутствующая дата. Проверены
  примеры 17:48, 18:02 и 15:12 при системном TZ=America/New_York.
- Компиляция MemoryUploadService/MemoryUploader против Android API 36.
- ESLint затронутых файлов и проверки типов сервера и клиента.

Тесты сервиса с module mocks запускаются отдельными Bun-процессами от тестов
реальных EXIF/репозиториев, чтобы не подменять их зависимости.

## Проверить на физическом Android

Полная сборка APK и сценарий на телефоне в этой сессии не выполнялись.
Проверить JPEG из галереи, несколько фото подряд, добавление второй пачки во время
первой, отмену текущего/ожидающего файла, сворачивание после подготовки, потерю
сети с ручным повтором, выход из аккаунта, повторное открытие путешествия.
Воспоминание должно попадать в календарный день съёмки после применения EXIF offset.

Начальная подготовка файлов ещё зависит от WebView. Очередь сервиса хранится
в памяти: force-stop/завершение процесса не равнозначны обычному сворачиванию
и не обеспечивают автоматического восстановления отправки. Проверки выше
не являются обещанием отсутствия любых ошибок на всех версиях Android/OEM.
Существующие вручную отвязанные даты не назначаются заново автоматически.
