# @limiteddissolve/obsidian-importer

Импорт путешествий из **Obsidian Vault** в **Trip Scheduler**: маршрут, day.meta-бейджи, активности, чек-листы, финансы, заметки и медиа.

## Возможности

- Автоматическое обнаружение вольтов и папок с турами (реестр Obsidian + маркер `.obsidian`, WSL-пути).
- Парсинг таймлайна дня, инфо-плашек `day.meta`, таблиц бронирований и чек-листов.
- Умная генерация активностей через LLM (AIHubMix / OpenAI: Gemini 3, Claude, DeepSeek V4, GPT-5.6) или офлайн-парсер.
- Извлечение координат из ссылок Яндекс Карт / Google Maps / 2GIS / OSM, геокодинг, индексация локальных медиа и загрузка галерей.

## Install

```bash
bun add @limiteddissolve/obsidian-importer
```

## Usage

```bash
bunx --bun @limiteddissolve/obsidian-importer \
  --api-url "https://trip-scheduler-api.limited-dissolve.ru" \
  --dir "~/Documents/obsidian-mark/Personal Note/Travel/-- Taiwan" \
  --start-date "2026-10-29" \
  --status draft
```

### Режим валидации (диагностика и аудит хранилища)

Перед импортом можно запустить глубокую проверку совместимости заметок Obsidian без записи в базу данных:

```bash
# Проверка из корня монорепозитория
bun run validate:obsidian -d "@/home/injurka/Documents/obsidian-mark/Personal Note/Travel/-- Taiwan/02 - Маршрутный план"

# Или гарантированно только проверить и завершиться без вопросов
bun run import:obsidian --validate --yes -d "~/Documents/obsidian-mark/Personal Note/Travel/-- Taiwan"
```

Валидатор автоматически:

1. Поддерживает пути вида `@/path/...` и разрешает подпапки (например, `02 - Маршрутный план`) к общему корню тура.
2. Проверяет структуру мастер-файла, наличие `## 📝 Краткое описание`, городов и тегов.
3. Проверяет синтаксис строк таймлайна и находит потенциально упущенные активности (пропущенные `**`, точки вместо двоеточий).
4. Проверяет существование локальных фотографий в папке `_` по ссылкам `![[...]]`.
5. Проверяет адаптивность `<iframe>` Google Maps и бейджи `day.meta`.
6. Формирует подробный отчет с оценкой совместимости в процентах (0–100%) и рекомендациями.

Для импорта используются `API_URL`, `ADMIN_EMAIL` / `USER_EMAIL` и `ADMIN_PASSWORD` / `USER_PASSWORD` (либо интерактивный вход). Для LLM-режима нужен `AI_HUBMIX_KEY` или `OPENAI_API_KEY`. Самостоятельный `--validate --yes` авторизации не требует.

### Сопоставление городов с каталогом

Перед созданием поездки или обновлением её метаданных импортер сверяет каждый город со справочником API и отправляет `cityIds`. Однозначные точные совпадения выбираются автоматически. В интерактивном режиме для неоднозначного/не найденного точного совпадения предлагается явный выбор из результатов каталога. С `--yes` неоднозначная подпись останавливает импорт до первой записи.

Для повторяемого non-interactive импорта передайте проверенный ID manifest через `--city-mapping`:

```json
{
  "version": 1,
  "mappings": [
    { "label": "Старый город из frontmatter", "placeId": "00000000-0000-5000-8000-000000000000" }
  ]
}
```

Пример вызова: `bun tools/obsidian-importer/src/run.ts --yes --city-mapping ./city-mapping.json ...`. Mapping применяется только к точному исходному label, выбранный ID проверяется через API, а manifest с лишними labels отклоняется. ID в примере — формат UUID, а не действительный place.

### Разделы бронирований: «Авто» и «Другое»

Строки сводной таблицы `Транспорт.md` раскладываются по разделам платформы по тексту колонки «Транспорт». Правила живут в `src/lib/transport-classifier.ts` — это единственный источник истины (его же использует разовая миграция):

| Что написано в «Транспорт»                                 | Раздел | Пометка (бейдж)  |
| ---------------------------------------------------------- | ------ | ---------------- |
| «🚖 Такси», «Яндекс Go», «Uber / Grab», «🚖 Шаттл / такси» | Авто   | Такси            |
| «Трансфер», «Шаттл», «в аэропорт»                          | Авто   | Трансфер         |
| «Авто с водителем», «с гидом»                              | Авто   | Авто с водителем |
| «Аренда / прокат авто»                                     | Авто   | Аренда авто      |
| «🚗 Личное авто», «машина»                                 | Авто   | Личное авто      |
| «🚌 Автобус», «bus», «🚌 Шаттл Taiwan Tourist Shuttle»     | Авто   | Автобус          |
| «🛵 Мотоцикл / скутер / мопед»                             | Авто   | Мото             |
| «⛴️ Паром», «корабль»                                      | Другое | Паром            |
| «⛵ Катер / лодка»                                         | Другое | Катер            |
| «🚡 Канатная дорога», «фуникулёр», «подъёмник»             | Другое | Канатная дорога  |
| «🚲 Велосипед», «электробайк», «самокат»                   | Другое | Вело             |
| «🚶 Пешком», «пеший переход»                               | Другое | Пеший переход    |
| «🚄 THSR», «🚆 TRA / EMU / поезд», «метро»                 | Поезда | —                |
| ни один признак не найден                                  | Другое | Прочее           |

Порядок правил важен: такси проверяется раньше трансфера («🚖 Шаттл / такси к причалу» — такси), а «автобус» — раньше «авто» (иначе подстрока «авто» перехватила бы автобус).

### Секции активностей: структурированный транспорт

Внутри активности используйте YAML-блок `transport`. Один блок описывает один вид транспорта и может содержать несколько последовательных отрезков. В режиме чтения Obsidian локальный плагин `Travel Transport View` показывает компактный маршрут, а importer разбирает его без LLM:

````markdown
```transport
type: metro
title: Taoyuan Airport MRT + Taipei MRT

routes:
  - from: Airport Terminal 2 (A13)
    to: Taipei Main Station (A1)
    line: Taoyuan Airport MRT
    code: A
    color: "#A93C93"
    direction: Taipei Main Station
    stops: 2
```
````

Для автобусов используется тот же формат с `type: bus`, `route`, `operator` и необязательным `walk`:

````markdown
```transport
type: bus
title: Chiayi → Hinoki Village

routes:
  - from: TRA Chiayi Station
    to: Hinoki Village
    route: Zhongxiao Xinmin Main Line
    code: Red A
    operator: Kuo-Kuang
    direction: Minxiong Industrial Park Service Center
    stops: 2
    walk: 95 м / 2 мин
```
````

Каждый элемент `routes` импортируется в порядке исходного YAML. Для `metro` importer создаёт `sections[]` с `type: "metro"`, `mode: "free"`, `systemId: null` и массивом `rides`, поэтому пересадки остаются отдельными отрезками. Для `bus` importer создаёт структурированную секцию с `type: "bus"` и массивом `rides` (маршрут, код, оператор, направление, остановки, пеший переход и цвет), которая полноценно отображается и редактируется на клиенте и сервере.

### GPX-треки в блоке «Маршруты» геолокации

В описании активности можно явно сослаться на `.gpx`-файл вольта — импортёр распарсит трек и создаст в геолокационной секции маршрут с геометрией и дистанцией. Длительность добавляется только при наличии временных меток точек GPX и отражает исходную запись, а не плановое время активности:

```text
* **08:00 - 14:00** — Восхождение на Цисин:
    * _GPX-трек_: [[xiao-you-keng-qi-xing-shan-....gpx|Сяоюкан — Цисин]]
```

Поддерживаемые формы ссылок:

- Obsidian-эмбед: `![[chinan.gpx]]`, с названием — `![[chinan.gpx|Тропа Чинань]]`
- wikilink: `[[chinan.gpx]]`
- markdown-ссылка на локальный файл: `[Тропа](Маршруты GPS/chinan.gpx)`
- «голое» имя файла в строке вида `**GPX-трек**: chinan.gpx`

Файл ищется внутри папки поездки и соседних общих папок вложений (полный относительный путь, однозначный суффикс пути или basename, без учёта регистра). При совпадающих именах укажите полный путь от корня поездки. GPX обрабатывается и в CLI, и в программном импорте, включая режимы `--no-images` и `--no-geo`. Отсутствующий или некорректный файл вызывает предупреждение. Если в строке упомянуты «вело»/«bike», маршрут получает режим «Велосипед», иначе — «Пешком». Название маршрута берётся из алиаса ссылки, затем `<name>` трека, затем имени файла. Клиент сохраняет импортированную геометрию (не пересчитывает её через OSRM) и позволяет экспортировать маршрут обратно в GPX из списка маршрутов.

Геометрия длиннее 1500 точек прореживается для отображения с сохранением начала и конца; дистанция рассчитывается по исходным точкам. Сверяйте начало, конец и направление GPX с планом дня: импортёр показывает содержимое файла и не перестраивает его под текст заметки.

Именованные точки `wpt`, `rtept` и `trkpt` извлекаются отдельно от геометрии. Точки в пределах 100 м от линии трека появляются в списке остановок в порядке прохождения, удалённые — отдельными POI. Имена у начала и конца заменяют стандартные подписи «Начало трека» и «Конец трека». Если именованных остановок нет, импортёр добавляет связующие точки коррекции (`connect`) через километр; для длинных треков интервал увеличивается, чтобы получить не более двадцати промежуточных отметок. Эти подписи обозначают расстояние от начала записи, а не названия достопримечательностей. Изменения видны после повторного импорта поездки.

### Конфигурационный файл (`importer.config.json`)

Вы можете настроить модели нейросетей, курсы валют для сметы, разделы по умолчанию, таймауты и параметры геокодинга через `importer.config.json` в корне проекта или передать путь флагом `-c, --config <path>`:

```json
{
  "defaultModel": "gemini-3.1-flash-lite",
  "mainCurrency": "RUB",
  "exchangeRates": {
    "TWD": 2.8,
    "USD": 90.0,
    "EUR": 100.0,
    "CNY": 12.5,
    "JPY": 0.65,
    "KRW": 0.07,
    "SGD": 70.0
  },
  "llmTimeoutMs": 45000,
  "batchSize": 8
}
```

### Programmatic API

```typescript
import { discoverVaultFolders, parseObsidianTripFolder, runImport } from '@limiteddissolve/obsidian-importer'

// Найти папки туров в известных вольтах
const folders = discoverVaultFolders('Travel')

// Разобрать папку тура в структурированные данные

// Полный импорт (интерактивный, если нет CLI-флагов)
await runImport()
```

### Точное время транспорта

В `Транспорт.md` используйте одну строку на одно направление и один вид транспорта.
Таблица: `Дата | Переезд | Транспорт | Время | Статус | Примечание`.
Дата: `03 ноя ➔ 04 ноя` для ночного переезда; часы — местные для каждой станции.
Время: `20:45–09:56`, одно отправление `около 11:30`, либо длительность `1–2 ч`.
Если часов нет, импорт сохраняет только дату и не подставляет 09:00–12:00.
При одном отправлении прибытие остаётся неизвестным. Резервные часы, дедлайны и
времена других рейсов пишите в примечании, не в колонке времени.
Номер поезда (`№270`), вагон (`вагон 12`) и место (`место 17`) заполняют поля карточки.
Перед справочной таблицей, которую не нужно превращать в бронирования,
ставьте `<!-- bookings:ignore -->`. Маркер действует на следующую таблицу.

### Метро: автоматическое сопоставление с городом

При обычном импорте CLI и программном `importTripFolderCore` блоки `transport`
с `type: metro` сопоставляются со справочником сервера (`GET /metro/systems`,
`GET /metro/systems/{id}`). Каталог запрашивается только при наличии метро и
кешируется на время одного запуска. Геокодирование и LLM для этого не нужны.

Город определяется по локации, названию и имени файла дня; Тайбэй распознаётся
также как Тайбей, Taipei, 台北 и 臺北. Линия определяется по `code` либо точному
нормализованному названию, станция — по коду вроде `R07` или точному названию
(английскому либо китайскому). Коды позволяют сопоставить `Chiang Kai-shek
Memorial Hall (R08)` с серверным `R08 C.K.S. Memorial Hall · 中正紀念堂`.

Если **все отрезки одного блока** однозначно относятся к одной системе,
импортер записывает `mode: city`, `systemId`, `lineId`, ID начальной/конечной
станций и канонические названия/цвета. Число остановок и направление считаются
по порядку станций выбранной ветки. Исходные ID отрезков сохраняются.

При отсутствии города/линии/станции, неоднозначном ответвлении или недоступности
API сохраняется исходный блок с ручным вводом; причина выводится в журнал.
Альтернативы вида `Zhongshan (R11) или Shuanglian (R12)` не превращаются в
случайно выбранную станцию. Блок с Airport MRT также останется ручным, пока эта
сеть не загружена в справочник. Блоки, уже имеющие `mode: city`, сохраняются.

Для проверки по живому справочнику **без записи поездки и документов**:

```bash
bun tools/obsidian-importer/src/run.ts --check-metro --yes \
  --api-url https://trip-scheduler-api.limited-dissolve.ru \
  --dir '/путь/к/-- Taiwan' --start-date 2026-11-04
```

Этот режим не требует авторизации, выполняет только GET-запросы и показывает
результат каждого блока. Указывайте фактический API вашей среды: без `--api-url`
адрес может переопределяться локальным `API_URL` из `.env`.
`--dry-run` и `--validate` по-прежнему работают без чтения серверного каталога;
`--check-metro` запускается отдельно от `--dry-run`.

Markdown переписывать не требуется. Чтобы применить новое сопоставление к уже
импортированной поездке, повторите обычную синхронизацию с её `--trip-id`.
Для карты необходимы координаты всех станций линии; наличие справочника без
координат уже позволяет использовать режим «По городу».

### Локации чек-листа на карте

Название локации остаётся в `location`, координаты сохраняются отдельно в
`locationCoords: { lat, lon }`. Старые текстовые локации поддерживаются; точку
можно выбрать в клиенте через поиск или клик на карте. Для импорта точной метки
укажите ссылку с координатами в поле локации:

```markdown
- [ ] Попробовать бэнто
  - _Где пробовать:_ [Название заведения](https://www.google.com/maps?q=23.504,120.695)
```

Координаты в примере иллюстрируют формат. Текстовые названия автоматически не геокодируются.

Строка `Локация` — метаданные пункта: она заполняет название и координаты
метки и не попадает в описание или поле обычной ссылки. Указывайте её один раз:

```markdown
- [ ] **Попробовать бэнто:** заказать у стойки
  - _Локация:_ [Название заведения](https://www.google.com/maps?q=23.504,120.695)
  - _Примечание к месту:_ Ориентир района; продавца выбрать на месте.
  - _Сайт:_ [Меню](https://example.com/menu)
```

Ссылки Google Maps, OpenStreetMap и Яндекс Карт не становятся обычным ресурсом
`link`; ссылка на сайт или меню сохраняется отдельно. Служебные строки локации
и повторные ссылки карты в старых записях также скрываются клиентом. Просмотр
метки открывает только карту; поиск и сохранение доступны отдельно при её редактировании.
