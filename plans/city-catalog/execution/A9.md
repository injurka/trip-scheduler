# A9 — offline snapshots, dumps and restore

**Status:** partial implementation; runtime restore and offline-device checks are still required.

## Что реализовано

- Новые офлайн-снимки получают `payloadSchemaVersion: 2`; записи без версии поднимаются в памяти как версия 1 и сохраняют старые `cities`-строки. IndexedDB structural version остаётся `1`, потому что формат поездки хранится в JSON и не требует изменения object store.
- Снимок сериализует весь актуальный объект поездки, включая `cityRefs`, `unresolvedCities` и `weatherByPlaceId`. Состояние Pinia меняется только после успешной записи в IndexedDB/localStorage, поэтому ошибка сохранения не затирает ранее сохранённую поездку.
- Новый дамп добавляет `geo/catalog.json` версии 1. Он содержит места, все их локализованные/curated names, country/version rows и необходимые audit/cache/link rows для ссылок из поездок, сегментов перелёта, метро, highlights, reviews и погоды. Глобальный каталог целиком в дамп не копируется.
- Restore читает новый geo-файл из локальной папки или S3 и восстанавливает geo FK в порядке `versions → catalog countries → places → names/cache/audit → app rows → trip links`. Старые дампы без файла продолжают читаться в legacy-режиме.
- Отсутствующий `geo/catalog.json` разрешён только для старых дампов; если файл есть, ошибка чтения или JSON-разбора останавливает восстановление. Ошибки чтения JSON-файлов дампа и листинга S3 также больше не превращаются в пустые массивы; S3-папки читаются с пагинацией. До очистки проверяются типы всех обязательных и переданных optional-коллекций.
- Перед очисткой базы seed-скрипт отклоняет неизвестную/неполную версию `geo/catalog.json` и незамкнутые geo-ссылки. Сам destructive restore не запускался.
- После восстановления referenced subset версии каталога получают состояние `loading`: частичная копия не будет ошибочно объявлена полным поисковым каталогом. После восстановления нужно повторно импортировать полный pinned GeoNames catalog, чтобы включить поиск.

## Проверки

- Статически сверены FK-порядок в `apps/server/db/schema.ts`, последовательность destructive cleanup/insert в `apps/server/db/seed-from-dump.ts` и пути локального/S3 чтения дампов. Ошибка чтения, парсинга или preflight происходит до destructive cleanup.
- Перед очисткой БД restore проверяет формат geo-файла, полноту его массивов и замыкание ссылок из прикладных данных. Ошибки вставки geo rows теперь останавливают restore, вместо тихого пропуска.
- `bun run lint:fix` и `bun run typecheck` пройдены; тесты и runtime-проверки восстановления не запускались.
- Никакой браузер/device offline round-trip, PostgreSQL restore, S3 restore или FK-сверка по восстановленной БД не выполнялись. Текущая чистая проверка runtime для этих критериев отсутствует.

## Ограничения и следующий шаг

Дамп самодостаточен для восстановления всех записей и отображения каждого сохранённого city ID без сети. Он намеренно не содержит весь GeoNames search corpus: после disaster restore сначала восстановить дамп, затем запустить обычный pinned catalog import и проверить `geo.catalogStatus` до открытия поиска пользователям. Старые офлайн-снимки остаются legacy-only и не получают ID без сети.
