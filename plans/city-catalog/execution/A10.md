# A10 — backfill audit and migration CLI

**Status:** CLI implementation prepared; no database audit or apply was run because there is no approved local/staging copy in this checkout.

## Commands

Run from the server package/container after migrations and full catalog import:

    bun run geo:backfill-cities audit --output /secure/path/geo-backfill.json
    bun run geo:backfill-cities apply --mapping /secure/path/geo-backfill.json
    bun run geo:backfill-cities apply --mapping /secure/path/geo-backfill.json --apply
    bun run geo:backfill-cities status --run-id <run-id>
    bun run geo:backfill-cities rollback --run-id <run-id>
    bun run geo:backfill-cities rollback --run-id <run-id> --apply

`apply` and `rollback` are dry-run unless the explicit `--apply` flag is supplied. The audit command writes a private mode-0600 JSON report to the requested path; it includes original city labels and must stay outside Git.

## Resolution and write rules

- The audit covers trip city positions, highlights, city reviews, metro systems and flight booking segments. The legacy name-keyed weather cache is reported only.
- Automatic selection is limited to one preferred, non-historical exact alias in a verified matching country. The report's suggested ID and `decisionSource` must remain unchanged for that path. Trips and flight segments without country context stay for manual review, even if the catalog returns one candidate.
- A reviewed mapping uses the exact report item key and source fingerprint. To select a non-suggested ID, set `placeId`, `decisionSource: "reviewed_mapping"`, `reviewed: true`, `reviewedBy` and a short `note`. The ID must exist, be active and satisfy the entity kind/country restrictions.
- Apply verifies catalog version and the complete item set before writing, then takes the advisory lock, locks each source row and rechecks its fingerprint inside one transaction. It stores the decision and before value in `geo_resolution_audit`, preserves original labels, and creates ordered trip links. Reusing a run ID is a no-op.
- Rollback checks the post-apply entity fingerprint first. If the trip, segment, profile record or metro row changed later, rollback stops instead of overwriting it.
