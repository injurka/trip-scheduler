# A2: загрузчик каталога GeoNames

Статус: **partial**

Дата: 2026-10-22

## Сделано

- Добавлена отдельная команда `apps/server/src/modules/geo/import-catalog.ts`. Она скачивает `cities500.zip`, `countryInfo.txt`, `admin1CodesASCII.txt` и `alternateNamesV2.zip`; проверяет зафиксированный SHA-256 `cities500.zip`; потоково разбирает ZIP через `unzip -p`; сохраняет населённые пункты по разрешённым feature codes и русские/английские альтернативные названия.
- Импорт по умолчанию работает как dry-run. Запись требует явного `--apply`; версии импортов адресуются хешами исходных файлов. Upsert использует стабильный UUIDv5 GeoNames ID, повтор той же опубликованной версии — no-op. Запись каталога и публикация версии выполняются в одной транзакции под advisory lock.
- Ручные `app_override` names сохраняются. Записи, отсутствующие в свежем cities500 subset, не удаляются: они отмечаются `sourcePresentInLatestSubset=false`.
- В PostgreSQL добавлена отдельная таблица `geo_catalog_countries`, keyed by source code. Связь с прежним справочником стран (`legacyCountryId`) nullable. Перед применением импорт показывает предложения, сопоставленные только по уникальному точному нормализованному совпадению названия из старого справочника с GeoNames RU/primary/ASCII именем. При `--apply` эти однозначные связи записываются в `countries.sourceCode`; неоднозначные и отсутствующие остаются несопоставленными. Dry-run требует DB read, но не меняет данные.
- После успешного применения команда выводит фактический `pg_total_relation_size` трёх таблиц вместе с индексами. Фактическое значение пока неизвестно: импорт и подключение к БД не запускались.
- В Docker-образ сервера добавлен `unzip`; команда `geo:import` зарегистрирована в `apps/server/package.json`.
- Prefix-поиск использует B-tree `text_pattern_ops` индекс из миграции `0015`; сравнение raw GeoNames primary/ASCII остаётся в отдельной таблице имён.

## Swarm / Portainer

`apps/server/src/server.ts` уже вызывает Drizzle `migrate()` перед запуском API. Отдельный migrator-service добавлять не нужно. После сборки и обновления образа новый сервер последовательно применит SQL-файлы из `/usr/src/app/drizzle`; миграции не содержат сотни тысяч городских строк.

После успешного старта API импорт запускается вручную из консоли его контейнера:

```sh
cd /usr/src/app/apps/server
bun run src/modules/geo/import-catalog.ts --data-dir=/tmp/geonames
bun run src/modules/geo/import-catalog.ts --data-dir=/tmp/geonames --apply
```

Первый запуск только скачивает/читает снимок и печатает контрольные количества. Второй пишет строки в PostgreSQL. Папка `/tmp/geonames` повторно используется между этими запусками только пока тот же Swarm task/container существует; флаг `--refresh` заново получает исходные файлы. Для импорта контейнеру нужен исходящий доступ к `download.geonames.org`, свободное временное место под ZIP-файлы и установленный `unzip` из нового образа.

Миграции и команду импорта в настоящем Swarm не применяли. API-поиск, выбор города в UI и ID-связи добавлены в A3–A8, но до импорта опубликованного каталога поиск не вернёт города.

## Следующий шаг

После того как образ с текущими изменениями будет опубликован и запущен в Swarm:

1. Убедиться по логам нового server task, что автоматические миграции завершились успешно, и проверить health API.
2. Запустить импорт без `--apply`; проверить контрольные количества, доступное временное место и отсутствие ошибок скачивания/разбора.
3. Повторить импорт с `--apply` и подтвердить готовность каталога через `geo.catalogStatus`.
4. Только после этого выполнить A10 audit старых пользовательских городов, вручную проверить отчёт и применить однозначные/проверенные сопоставления.

Команду импорта и backfill сначала следует выполнить на тестовой или резервной копии БД, если она доступна. Не использовать `db:seed-dump`: это destructive restore дампа, а не запуск миграций.
