# Справочник городов по ID: исследование и план для LLM-агентов

Дата исследования: **22 октября 2026**, Europe/Moscow. Проверенный checkout: `6939e83dae39c11515adc79a573a601b0633b6dd`. Это пакет для последующей реализации; приложение и рабочая БД в рамках исследования не изменялись.

К моменту сохранения пакета HEAD обновился до `f564062d41f6c1af9d3a428cb5d4f53bf33b9ffe` за счёт параллельной работы вне этого исследования. Ключевые поля `trips.cities`, `highlights.city` и `destinationReviews.city` повторно сверены: модель осталась строковой. Будущим исполнителям всё равно требуется A0 на своём checkout.

Цель: заменить свободный ввод в структурированных полях городов выбором проверенного места из локальной БД. Сохранять ID, показывать понятное название со страной и регионом. Существующие поездки, импорт, погода, карты, профиль и офлайн-чтение должны пережить переход.

Специальная запись или отдельное правило разрешения для «Акташа» в исходный объём не входят.

## Рекомендация

Использовать локальный импорт **GeoNames cities500**, отфильтровав исторические, разрушенные и заброшенные места, районы городов и группы населённых пунктов. В загруженном снимке **236 632** строки; после предложенного фильтра — **225 823**. Архив занимает **13 900 649 байт**, распакованный TSV — **41 716 248 байт**. Указанные в README GeoNames ориентиры «185 тысяч» и «130 тысяч» не являются фактическим числом записей сегодняшних архивов.

Для сравнения, сегодняшний cities1000 содержит **171 572** строки, после того же фильтра — **161 881**. Источник и SHA-256 зафиксированы в JSON-отчётах. Каталог не претендует на все существующие места мира.

Размер PostgreSQL с русскими названиями и индексами пока **не измерен**. Предыдущая оценка 30–80 МБ была предположением; использовать её как установленный размер нельзя. Измерение реальной БД и поисковых запросов включено в обязательный этап A2.

## Как запустить выполнение агентами

Передать оркестратору следующий запрос:

> Реализуй переход Trip Scheduler на справочник городов и мест по ID по пакету `plans/city-catalog/`. Сначала прочитай README, research.md, implementation-plan.md и agent-tasks.md, затем актуальные правила репозитория. Выполняй задания A0–A11 по зависимостям. Параллельно делегируй только задачи из одной разрешённой волны с непересекающимися файлами. Зафиксируй контракт до работы зависимых агентов. Сохрани посторонние изменения в checkout. Начни с A0 и представь фактическую матрицу покрытия старых данных и план переключения. Пиши и проверяй реализацию в изолированной локальной среде; применение к production, коммит, тег и публикация требуют отдельного запроса. Не считай завершением один новый селект: проверь API, миграцию, фильтры, импорт, погоду, карты, офлайн и восстановление дампа. Отмечай выполненные задания и сохраняй отчёты в `plans/city-catalog/execution/`.

Это инструкция для **будущего выполнения**, а не свидетельство, что оно уже началось. В `agent-tasks.md` находятся отдельные задания для исполнителей.

## Что пока неизвестно

- Состав городов в актуальной пользовательской БД и количество неоднозначных/не найденных значений: рабочая БД не опрашивалась.
- Покрытие предпочтительными русскими названиями: языковые alternateNamesV2 не импортировались.
- Реальный размер таблиц и индексов, RAM при импорте, задержки поиска: PostgreSQL-стенд не создавался.
- Политика поддержки старых установленных мобильных/десктопных версий: до её утверждения legacy API сохраняется.

Неизвестные значения являются входом A0/A2 и воротами переключения, а не разрешением агентам додумать данные или назначить город по наиболее похожему названию.
