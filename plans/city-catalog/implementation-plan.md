# План реализации каталога городов и перехода на ID

Статус: реализация начата; общая схема, GeoNames loader и первый API поиска добавлены, полный переход форм и данных ещё не завершён. Основание и фактические измерения — [research.md](research.md). План описывает полный переход структурированных полей; порядок выдачи задач — [agent-tasks.md](agent-tasks.md).

## 1. Результат для пользователя и границы

1. В создании/редактировании путешествия, фото профиля, отзыве о городе и городах авиасегмента выбирается запись справочника. Произвольная строка не создаёт новый город.
2. Поиск принимает русские, исходные и проверенные альтернативные названия. Результат показывает имя, страну и регион. Для одинаковых имён доступны разные ID.
3. Выбранные места сохраняются по ID. Переименование города не меняет его идентичность. Координаты каталога используются для карты города и климата.
4. Старые записи остаются читаемыми, в том числе офлайн. Неоднозначные старые названия явно учитываются в отчёте миграции и не превращаются в случайный ID.
5. Все самостоятельные формы создания и редактирования охвачены; искать по семантике данных, а не только по надписи «Город».

| Данные | Поведение после перехода |
| --- | --- |
| `trips.cities` | Канонические связи с каталогом, порядок сохранён; старое поле временно используется как совместимая проекция |
| `highlights.city` | Nullable FK на этапе миграции; обязательный ID при новом ручном выборе; страна проверяется на сервере |
| `destinationReviews.city` | ID обязателен для нового `type=city`; у `type=country` ID города отсутствует |
| `FlightSegment.departureCity/arrivalCity` | Новые `departureCityId`/`arrivalCityId`; строки — отображаемый/source snapshot, не альтернативный путь произвольного выбора |
| Город системы метро | Дополнительный `geoPlaceId`, когда сопоставление подтверждено; `systemId`, линии и станции сохраняют собственную идентичность |
| Исходные EXIF, текст билета, названия в Markdown | Сохраняются как исходные данные; становятся кандидатами для resolver, а не доверенными ID |
| Адрес отеля, станции, аэропорты, POI, точки маршрута, GPX, текст заметок | Сохраняют свою семантику и точные координаты. Автоселект города не заменяет эти сущности |

Базовый каталог — населённые пункты cities500. Подтверждённые направления вне этого набора добавляются по конкретным внешним GeoNames ID в небольшом versioned manifest. Для острова допустим тип `island`, для региона/парка — отдельный явно проверенный тип `area`. Они доступны в направлениях путешествия; поля «город» профиля/перелёта ограничены `settlement`. Не создавать глобальный каталог POI в рамках этой задачи. Отсутствие названия в справочнике не доказывает, что место не существует.

## 2. Решения, общие для всех агентов

### 2.1 Источник и обновление

- GeoNames `cities500.zip`; allowlist из research.md. Число строк брать из manifest импорта, не зашивать сегодняшнюю цифру в код.
- Данные находятся в серверной PostgreSQL. В клиентский bundle не включать мировой JSON и весь список aliases.
- Исходные ZIP и языковые данные загружаются отдельным CLI, а не при старте сервера, не в SQL-миграции и не в install hook.
- Версия снимка: URL, дата загрузки UTC, SHA-256 каждого файла, source Last-Modified при наличии, версия importer/filter, число принятых/отклонённых записей.
- Сначала staging и проверки, затем атомарное объявление готовой версии; частично загруженный каталог не становится активным. Повторный импорт того же снимка идемпотентен.
- Upsert по source key сохраняет ID. Исчезновение из **поднабора cities500** не означает удаления из мира: сохранить referenced record, отметить отсутствие в свежем subset, проверить отдельно. Явное source deletion переводит запись в retired; FK не удалять каскадом, старые references гидратируются.
- Старые версии приложения читают retired refs; новый поиск не предлагает их для нового выбора. Обновление данных не меняет существующие связи автоматически.
- Атрибуция GeoNames и CC BY 4.0 доступна в интерфейсе/документации и распространяемых выгрузках.

### 2.2 Предлагаемая модель PostgreSQL

Имена ниже — зафиксированный словарь для задач. В A1 уточнить типы Drizzle и отношения, не переименовывать сущности разными агентами.

| Сущность | Поля и ограничения |
| --- | --- |
| `countries` | Существующий `id` сохранить. Добавить nullable unique `sourceCode` (двухбуквенный код территории GeoNames, нормализованный uppercase) для проверенной связи legacy-справочника |
| `geo_catalog_countries` | Канонические страны источника по `code`, GeoNames ID и source names. `legacyCountryId` nullable: полный каталог не зависит от угадывания между GeoNames и прежними внутренними country IDs |
| `geo_catalog_versions` | ID версии, manifest JSON, checksum, state `loading/ready/failed`, времена, counts, версия importer |
| `geo_places` | `id uuid PK`, `source='geonames'`, `sourceId text`, unique `(source, sourceId)`, `countryCode FK geo_catalog_countries.code`, `featureCode`, `kind settlement/island/area`, primary/ascii name, `latitude/longitude double precision`, `admin1Code/admin2Code`, region label, timezone, population, source modified date, catalog version, retired/subset status |
| `geo_place_names` | `placeId FK`, language (включая пустое значение для неизвестного языка), name, normalized/prefix key, origin, preferred/historical flags, version. Dedup по месту/языку/нормализованному имени; проверенные overrides не стирать обновлением источника |
| `trip_geo_places` | `tripId FK`, `position`, nullable `placeId FK`, nullable `legacyLabel`, resolution status. PK `(tripId,position)`; CHECK запрещает resolved без placeId и unresolved без сохранённой строки. Удаление поездки удаляет связи; удаление каталога не каскадирует поездки |
| `highlights`, `destinationReviews` | Добавить nullable `geoPlaceId FK`; старую строку сохранить до завершения миграции. Требования к типу/стране проверять сервером; не объявлять FK NOT NULL до обработки исторических исключений |
| `metroSystems` | Добавить nullable `geoPlaceId`; отдельный mapping систем, а не вычисление ID из названия |
| `geo_weather_cache` | Новый кэш по `(placeId,month,generationVersion)`; хранить fingerprint координат/входов генерации и считать изменение fingerprint cache miss |
| `geo_resolution_audit` | migrationRunId, entity type/ID, позиция или segment/field path, исходная строка, использованный контекст, status/reason, candidates, chosen ID, rule/override provenance, before fingerprint |

Внутренний UUID для GeoNames вычислять детерминированно: UUIDv5 от строки `https://www.geonames.org/<sourceId>` в стандартном URL namespace. Строка и namespace фиксируются контрактным тестом. Внешний числовой ID хранится как `sourceId` и не подменяет ID метро/билета/пользовательской записи. Детерминированность облегчает пересоздание каталога и восстановление; provider redirect/merge обрабатывать отдельно, не переиспользовать чужой ID.

Country mapping — явный versioned артефакт с проверенными соответствиями. Существующие UUID/прочие text ID не заменять ISO-кодами. Не использовать country name, порядок массива или ближайшую страну как постоянный ключ. Для отсутствующих country records предусмотреть отдельное проверенное добавление, не молча терять города. TW/HK и другие особые коды сохраняют различие источника и существующие подписи приложения.

### 2.3 Русские имена и aliases

- Language-aware имена импортировать из alternateNamesV2, отбирая только place IDs выбранного каталога. Базовый объём — ru/en и исходные имена; native aliases включать ограниченным, измеряемым набором. Случайные метки iata/post/wiki-ссылки не превращать в названия города.
- Не загружать всю таблицу aliases в память процесса. Полный исходный файл может быть намного больше cities500; обработка потоковая, временное место и RSS измеряются.
- Отображение: проверенный app override → preferred/nonhistoric ru → другой nonhistoric ru по детерминированному правилу → primary name. Не обещать русский перевод каждой записи.
- Исторические aliases можно искать с пониженным приоритетом, но они не дают автоматическое право мигрировать старую строку.
- Нормализация служит поиску. Сохранять исходное имя; ё/е, NFKC и диакритика не являются правилом слияния сущностей. Не генерировать переводы и соответствия через LLM.

## 3. API и переходный контракт

Новый router: `geo` в `apps/server/src/modules/geo/`, repository/service через `measureDbQuery`. На клиенте — `IGeoRepository`, реализация в существующем `shared/services/api/` и поле `db.geo`.

Source of truth DTO — Zod-схемы сервера, клиент выводит типы из tRPC по текущему паттерну проекта. Опубликованный `@limiteddissolve/obsidian-importer` имеет собственный лёгкий transport interface и проверяется интеграционными контрактными fixtures. Не добавлять в него runtime import из server/client или private workspace package: это сломает отдельную установку CLI.

### 3.1 Read API

```ts
type GeoPlaceRef = {
  id: string // внутренний UUID
  name: string // отображаемое имя выбранной locale
  countryId: string | null // existing app country ID only when explicitly mapped
  countryCode: string
  countryName: string
  regionName: string | null
  kind: 'settlement' | 'island' | 'area'
  latitude: number
  longitude: number
  timezone: string | null
  retired: boolean
}

geo.search({ query, countryId?, kinds?, locale: 'ru' | 'en', limit? })
// { items: GeoPlaceRef[], catalogVersion: string }

geo.getByIds({ ids, locale })
// { items: GeoPlaceRef[], missingIds: string[], catalogVersion: string }
```

- Query trim, min 2 и max 100 символов; limit по умолчанию 20, верхний предел 30. Пустой запрос не выгружает каталог. getByIds ограничен, например, 100 ID на запрос; точные пределы отражаются и в Zod, и в документации.
- Search: exact primary/preferred → prefix → ограниченный fuzzy fallback. Учитывать страну и kind, затем population/relevance, стабильный ID tie-break. Dedup по ID до LIMIT, чтобы aliases не заполняли страницу повторениями.
- Двухсимвольные запросы идут по индексируемому prefix-пути; для длинных запросов — проверенный индексированный pg_trgm. Экранировать `%`/`_` при буквальном вводе, параметризовать запросы, ограничивать стоимость и частоту. Функция similarity в SELECT без индексируемого WHERE не считается готовым поиском.
- Сначала проверить доступность pg_trgm в фактической PostgreSQL 16. При отсутствии прав на extension сохранить exact/prefix-режим и сообщить ограничение; не заменять его полным ILIKE-сканированием на каждую букву.
- `getByIds` возвращает retired places и служит гидратации выбора, публичного чтения и офлайн-снимков. Не выдаёт private trip data. Недостающий ID не получает выдуманный label.
- Кэш ограничен размером/TTL, учитывает query/country/kinds/locale/catalogVersion. Не кэшировать бесконечно все запросы.

### 3.2 Write API

- Новая запись/явное изменение списка городов поездки принимает `cityIds: UUID[]`; порядок значим, новые дубли отклоняются. Все ID и kinds проверяются, вся операция с поездкой/связями транзакционна.
- Фото/отзыв принимают `geoPlaceId`; координаты самого фото/отзыва остаются координатами записи. Если прислан countryId, он должен совпасть с записью каталога; можно выводить страну на сервере из placeId.
- В новом авиасегменте при ручном выборе города сохраняются `departureCityId`/`arrivalCityId`, плюс snapshot строки для старого чтения. Аэропорт/IATA/терминал/точные координаты и времена не меняются от выбора города.
- Контент bookings сейчас проходит как `z.any()`: добавить targeted runtime validation/resolution city IDs в пути create/update секций и server import. Проверять вложенные сегменты, а не доверять DTO клиентского picker. Остальные поля секции сохранять.
- Для нового/изменённого ручного city label отсутствие ID не является обходом проверки: сравнить с прежней legacy-записью либо отклонить. Сохранение необязательного сырого текста распознанного билета выполняется доверенным серверным extraction/import путём; клиентский `source=import` флаг не даёт таких полномочий. Строка snapshot при ID формируется сервером, а не принимается как второе независимое значение.
- Public catalog write API не предоставлять. Курируемые исключения — CLI/manifest с реальным внешним ID и provenance.

### 3.3 Совместимость

Во время expand/migrate/cutover `cities: string[]` и строки профиля остаются read-проекцией для старых клиентов; новые клиенты получают дополнительно `cityRefs` и `unresolvedCities` с position. Центральный mapper собирает одинаковый ответ для list, byId, withDays, shareSlug, user lists и последующего offline save.

Нельзя заменить тип существующего `cities` на UUID[] без смены контракта: старое приложение покажет UUID пользователю. Не менять старое поле на array of objects под тем же именем.

- При PATCH без изменения городов старые нерешённые entries сохраняются. Новый клиент отправляет `cityIds` только при изменении выбора; перед такой отправкой все остающиеся legacy chips должны быть разрешены либо явно удалены пользователем.
- Для старого клиента прежний неизменившийся массив названий сохраняет existing links/legacy entries. Изменённые новые строки проходят строгий resolver; ambiguous/not-found дают структурированную ошибку и инструкцию обновить приложение/уточнить выбор. Новые произвольные записи в глобальном каталоге не создаются.
- Если одновременно присланы canonical ID и legacy строки, проверить согласованность или отклонить конфликт; нельзя молча выбрать один вариант.
- Уникальность старого отображаемого ключа для двух одноимённых мест обеспечивать подписью со страной/регионом. Это особенно важно для legacy `weatherData` и фильтров; нельзя перезаписывать один город другим по имени.
- Для новых URL использовать `cityIds`/`cityId`; старые `cities`/`city` разбирать в совместимом adapter. Неоднозначная старая ссылка не должна тихо выбрать крупнейший город.
- Удаление legacy API и колонок — отдельный поздний этап после решения по поддержке установленных native-клиентов. Завершение перехода текущего UI не требует немедленного удаления совместимого API.

## 4. UI и остальные потребители

### 4.1 Общий выбор города

Два слоя: API-независимое расширение `01.kit/kit-select-with-search` и доменный `03.domain/geo-place-picker` с composable/repository. Фичи импортируют домен, не друг друга. В `01.kit` не помещать API или Pinia.

- Добавить controlled search event/model и режим внешней фильтрации без поломки локальных селектов.
- Выбранные refs хранить/гидратировать отдельно от текущей страницы результатов. Поиск другой строки, закрытие меню, сбой сети и перезагрузка не превращают labels в UUID.
- Debounce около 250 мс, защита от устаревшего ответа по request token; отмена не должна показываться ошибкой. Смена страны сбрасывает несовместимый выбор с понятным состоянием.
- Страна/регион видны для каждого результата; поиск русского и латинского имени приводит к одному ID.
- Новые произвольные chips не создаются; Enter без выбранного результата ничего не сохраняет.
- Состояния: загрузка, пустой результат, offline, временная ошибка, retired выбранное место, legacy «требует уточнения». Сбой API не равен «города не существует».
- Keyboard/фокус/Enter/Escape, accessible roles, scroll, touch, multi-select и удаление chips проверить в живом интерфейсе. Не использовать raw object equality как идентичность места.
- Без сети доступны сохранённые refs; глобальный поиск показывает ограничение. Возможность создания полностью офлайн-путешествий в текущей архитектуре отдельно подтверждается A0; мировой каталог на устройство по умолчанию не загружается.

### 4.2 Обязательные формы

- Создание путешествия через trips-hub и редактирование через trip-edit-info-dialog.
- Highlights create/edit, повторное использование места прошлого фото, EXIF-подстановка и копирование записи.
- Destination-review create/edit **и** отдельный destination-review-form; подтвердить, какие формы реально подключены, затем покрыть все активные пути.
- Flight-card: оба ручных города каждого сегмента, включая пересадки.
- Фильтры списка поездок, публичных поездок пользователя, фото и отзывов; query-sync и старые ссылки.

### 4.3 Карты и климат

- Для cityRefs карты используют координаты каталога; порядок координат проверять на каждом интерфейсе: DTO lat/lon против MapLibre `[lon,lat]`.
- Маркер фотографии/отзыва, станции, аэропорта и POI сохраняет точную пользовательскую точку. Перевыбор города не переносит фотографию в центр города.
- В новом weather API выбирать `placeId`. Кэш — `geo_weather_cache`, payload поездки дополнить `weatherByPlaceId`; существующий `weatherData` остаётся legacy-проекцией. Не менять формат старого поля без adapter.
- Генерация использует канонические координаты и подпись места. Строковые кэши переносить только при подтверждённой идентичности/географии; при сомнении cache miss и регенерация, а не переименование ключа.
- Проверить одиночную/пакетную/forceRefresh генерацию, выбор города в weather widget и оба одноимённых города одновременно. Идемпотентный upsert не создаёт две кэш-строки при параллельных запросах.

### 4.4 Импорт и AI

- Markdown/frontmatter оставлять удобным для человека: имена допустимы как сырьё parser. Resolver выполняется **до** записи cityIds в trip metadata.
- Обновить оба пути `lib/import-trip.ts` и `cli/importer.ts`, transport interface/API client, а также server AI flow через `importTripFolderCore`.
- Resolver возвращает `resolved/ambiguous/not_found` с candidates и provenance; batch endpoints не создают места из строк.
- CLI: dry-run выдаёт отчёт; interactive режим позволяет выбрать кандидата; noninteractive режим принимает заранее подготовленный mapping manifest. Никакого автоматического «первый результат».
- Noninteractive импорт с unresolved обязательными городами останавливается до изменения города существующей поездки/создания новой; уже сохранённое не затирается пустым списком. Server AI job переводится в явное failed/needs-input состояние, поддерживаемое текущим протоколом, с читаемой причиной.
- Для необязательных распознанных city labels в билетах raw source можно сохранить без ID как `unresolved`; ручное изменение такого города требует picker. Не терять билет из-за отсутствия необязательного enrichment.
- Передавать display names в существующие location/metro context эвристики, которым нужен текст; не запускать regex по UUID.
- IATA, airport coords и город обслуживания аэропорта — разные данные. Не назначать город автоматически по ближайшему центру и не переписывать timezone offset билета из city timezone.

## 5. Миграция существующих данных

### 5.1 Аудит без записи (A0)

На согласованном локальном dump/staging: собрать все distinct labels, country IDs, число ссылок, координаты при наличии, тип/позицию/путь записи. Включить trips, highlights, reviews, metro и flight segments в JSONB; исходные EXIF и свободные тексты учитывать как контекст, не переписывать.

Отчёт содержит counts, пустые/повреждённые значения, alias collisions, не-населённые пункты, country mapping gaps и пробный resolver. Пользовательские данные не публиковать в репозитории: в git только агрегаты/анонимизированные fixtures, полный audit — локальный защищённый артефакт.

### 5.2 Правила разрешения

1. Существующий подтверждённый ID или explicit mapping для конкретной записи/контекста имеет приоритет.
2. Точное primary/preferred nonhistoric alias с согласованной страной/регионом/смыслом и единственным кандидатом допускает auto-resolve по зафиксированному правилу. Если контекста нет или источник строки неясен, оставить review candidate даже при одном видимом совпадении.
3. Координаты и регион помогают проверке; nearest-city само по себе не доказывает место назначения. У фото/аэропорта точки могут находиться далеко от обслуживающего города.
4. Нечёткое совпадение, перевод, краткий исторический alias, преобразования ё/е, «самое большое население» и равные кандидаты не допускают auto-apply.
5. Остров/регион не превращается в город автоматически. Курируемое добавление требует точной записи источника и подходящего kind.
6. Не создавать глобальные alias-записи для неоднозначных названий. Любой ручной override должен иметь достаточный scope: entity/position, country+region или подтверждённый контекст.

### 5.3 Применение

- Новый CLI `audit/resolve/apply/status` с dry-run по умолчанию. Явный apply использует утверждённый mapping manifest и runId.
- Применение пакетами в транзакциях, с проверкой fingerprint/updatedAt исходной записи. Изменившиеся после аудита записи пропустить с conflict, не перезаписать пользовательскую правку.
- Хранить исходные labels и решения в audit. Сбой/повторный запуск не дублирует связи и не меняет уже проверенные сопоставления.
- Сначала импорт каталога и country mapping, затем trip/profile/flight bindings, затем weather/metro associations. Встроенные операции backfill не должны обращаться к публичному геокодеру для каждой строки.
- Unresolved старые записи сохраняют читаемый label и статус. Они не считаются завершённой миграцией: финальный отчёт перечисляет их и принятую политику каждой группы.
- Перед строгим переключением новых клиентов на ID обработать все пользовательские случаи из утверждённого scope либо зафиксировать явные legacy-исключения. Не объявлять «все города заменены», пока исключения существуют.

## 6. Офлайн, seed и восстановление

- Вместе с поездкой сохранять полные выбранные refs и weatherByPlaceId, а не только ID. Мировой каталог для чтения офлайн не нужен.
- Ввести `payloadSchemaVersion` для OfflineTripEntry/нормализатора. Версия IndexedDB увеличивается только при реальном изменении object stores/indexes; новая форма JSON сама по себе не требует удаления/пересоздания БД.
- Старый snapshot с `cities:string[]` нормализуется локально без сети и остаётся читаемым. Возможное обогащение refs при появлении сети — отдельная операция с durable save и сохранением предыдущего состояния при сбое.
- Проверить localStorage legacy migration/fallback и отсутствие потери сохранённых поездок. Полный каталог в localStorage не помещать.
- Дамп сохраняет внутренние ID, source keys, нужные refs, aliases/overrides и версии. Выбрать self-contained стратегию: включать все referenced places плюс необходимые names; глобальный seed-каталог можно восстановить отдельно из pinned manifest. Стратегию описать в версии dump format.
- Restore без сети обязан восстановить все referenced places, включая curated/retired, до FK-связей. Отсутствующий глобальный источник не превращает restore в потерю записей.
- Старые дампы читаются в legacy mode с последующим явным resolver. Текущий destructive seed-from-dump не запускать на пользовательской БД как способ импортировать справочник.
- Mock seed содержит детерминированный малый набор городов и links; e2e не зависит от живого GeoNames. Не генерировать 200 тысяч mocked опций в UI.

## 7. Проверки и ворота качества

Проверять реализацию по изменённым путям и интеграционным сценариям; один typecheck не подтверждает поведение. Точные команды пакетов проверить по актуальным package.json. Правила проекта предусматривают `bun run lint:fix`, затем `bun run typecheck`; выполнять на контролируемом change set, проверяя diff, поскольку formatter может затронуть посторонние изменения.

| Группа | Обязательное доказательство |
| --- | --- |
| Схема/импорт | Чистая и существующая локальная БД; повторный импорт; malformed ZIP/TSV; оборванная загрузка; отсутствующая страна; retired/subset disappearance; FK integrity; отсутствие публикации частичного snapshot |
| Поиск | Русский/латиница/диакритика, 2 символа, пустой/длинный ввод, literal `%/_`, одинаковые названия в одной стране, deterministic ranking, limit после dedup |
| Валидация | Неизвестный/retired/wrong-kind ID, несогласованная страна, дубли, конфликты legacy и ID, deep city IDs в bookings; raw mutation не обходит picker |
| Миграция | Alias «Hiroshima» с несколькими кандидатами остаётся на проверке; остров не становится городом; dry-run ничего не пишет; повтор apply; concurrent edit конфликт; восстановление исходных связей по audit |
| Совместимость | Старые API-проекции и текущие ID DTO, все read endpoints, старые filter URLs, PATCH заголовка старой поездки без изменения городов |
| UI | Create/edit поездки, highlights, все активные review forms, flight segments; keyboard/touch, запросы с переставленным порядком ответов, исчезновение выбранной опции, ошибка сети, две одноимённые сущности |
| Карты/погода | Нет геокодинга имени для resolved ref; сохранены реальные точки фото/аэропорта; `[lon,lat]`; разные cache keys для одноимённых городов; label rename не смешивает данные |
| Импорт | CLI и core, server AI, интерактивный mapping, noninteractive unresolved fail до city write, повторный импорт, human-readable context, booking raw-source сохранён |
| Offline/backup | Новые и старые snapshots при отключённой сети, reload, storage failure, локальный restore с refs без сети, старый dump, сохранены пользовательские ID и порядок |

Производительность — предлагаемая цель, не существующее обещание: p95 серверного city search ≤150 мс на зафиксированном staging под согласованной нагрузкой; начальный benchmark — 10 параллельных запросов. Указать hardware, PostgreSQL version/collation, число places/names, cold/warm cache, queries и error rate. Если цель не достигнута, исследовать план запроса до добавления отдельного поискового сервиса.

Размер: измерить `pg_table_size`, `pg_indexes_size`, `pg_total_relation_size` для places/names/cache, число aliases, общий catalog bytes, import wall time/peak RSS и размер выбранных refs в ответе. Приложить `EXPLAIN (ANALYZE, BUFFERS)` на локальном стенде для short/exact/prefix/fuzzy и country-filtered запросов. Слово «быстро» без данных не закрывает A2/A3.

## 8. Порядок включения и откат

1. **Expand:** additive schema, старые поля доступны; каталог загружается отдельно. Новый search пока не используется в пользовательских write forms.
2. **Prepare:** собрать фактические country mappings, покрытие, размеры и кандидатов миграции. Локальная проверка restore до любых production операций.
3. **Backend readiness:** read adapters, strict ID writes, legacy resolver, booking deep validation и offline-compatible DTO готовы. Legacy write policy согласована и описана.
4. **Migrate:** применить утверждённые mapping decisions на staging; затем после отдельного разрешения — на целевой БД. Live writes не теряются, ambiguous остаются видимыми.
5. **Cutover:** включить picker и остальные ID-потребители одним согласованным переключением `geoCatalogUiEnabled` после готовности зависимостей. Частичные feature flags по доменам возможны для staging, но общая приёмка требует весь scope.
6. **Observe:** unknown ID, unresolved, поисковые ошибки/latency, конфликты миграции, ошибки legacy clients и storage/restore отслеживаются отдельно.
7. **Contract cleanup:** только после утверждённой политики версий и обработки исключений можно удалить legacy writes/поля. Отдельная миграция и релиз.

Откат UI — выключить picker flag и вернуть совместимый путь, сохраняя новые refs/каталог. Откат backfill — по runId и before fingerprint, только если после миграции запись не редактировалась; иначе conflict/manual review. Автоматически удалять каталог/новые связи для rollback нельзя. Перед production apply требуется проверенный backup и отдельное разрешение владельца; этот план авторизует подготовку и локальную реализацию.

## 9. Что считать завершением

- [ ] Все активные ручные **поля города** из scope используют общий выбор по ID; в booking UI нет оставшегося текстового обхода.
- [ ] Прямой API-запрос не создаёт случайный город и не принимает несуществующий/неподходящий ID.
- [ ] Версионируемый каталог и country mapping воспроизводимы; повторное обновление сохраняет IDs и references.
- [ ] Старые labels сохранены; каждое unresolved значение имеет явный статус/решение, и отчёт не выдаёт его за успешную миграцию.
- [ ] Все trip read paths, фильтры, профиль, метро associations, импорт, AI, карты, weather, offline, dump/restore проверены.
- [ ] Фактический размер PostgreSQL, aliases/indexes, импорт RAM/time и search latency приложены.

- [ ] UI подтверждён в работающем браузере; native/offline доказательства перечислены отдельно. Не проверенное устройство не помечено проверенным.
- [ ] Сохранён scope посторонних dirty-файлов; нет незаказанного commit/tag/deploy.
- [ ] Передан эксплуатационный runbook: import/update, audit/apply, exceptions, diagnostics, restore, rollback и совместимость старых версий.
